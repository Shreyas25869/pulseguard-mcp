## Executive Summary
During the development of **PulseGuard MCP**, we built an open-standard Model Context Protocol (MCP) server designed to bridge Alexa+ agentic reasoning with smart home actuators (Ring Video Doorbell, Smart Deadbolts) and ambient health telemetry.

Below is an authentic, structured record of developer friction points encountered across **Amazon Bedrock Converse API**, **MCP Schema Serialization**, and **Alexa+ Simulation Workflows**, along with our workarounds and actionable engineering recommendations for Amazon's developer tooling teams.

---

### Friction Entry 1: Schema Incompatibility between MCP `zod` Schemas and Amazon Bedrock Converse Tool Definitions

* **Task Attempted:**  
  Directly mapping Model Context Protocol tool specifications generated via `@modelcontextprotocol/sdk` (which uses Zod v3 schemas) into the Amazon Bedrock `ConverseCommand` `toolConfig.tools[].toolSpec.inputSchema.json` property.

* **Steps Taken:**
  1. Defined MCP tools using `server.tool(name, zodSchema, handler)`.
  2. Extracted the resulting JSON Schema via `zod-to-json-schema`.
  3. Passed the schema directly to `BedrockRuntimeClient.send(new ConverseCommand({ ... }))`.

* **Expected vs. Reality:**
  * **Expected:** Bedrock Converse API would parse standard JSON-Schema Draft 7 definitions generated by standard MCP libraries.
  * **Actual:** Bedrock rejected the payload with `ValidationException: The inputSchema does not conform to the expected format. Property 'additionalProperties' or '$schema' is not supported at /toolConfig/tools/0/toolSpec/inputSchema/json`.

* **Severity:** **High (Blocked development for ~3.5 hours)**

* **Workaround Implemented:**  
  Created a custom schema sanitizer utility (`server/mcp/tools.ts`) that recursively strips `$schema`, `additionalProperties`, and `definitions` properties before dispatching the payload to Bedrock.

* **Actionable Suggestion for Amazon:**  
  Release an official `@aws-sdk/mcp-bedrock-bridge` package or update the Bedrock Converse API parser to automatically ignore metadata keywords (`$schema`, `description`, `additionalProperties`) so that standard MCP servers work out-of-the-box with Bedrock without custom sanitizers.

### Friction Entry 2: Tool Return Payload Serialization Mismatch in Multi-Turn Bedrock Conversations

* **Task Attempted:**  
  Returning structured JSON telemetry (containing nested patient vitals arrays, Ring status, and prescription objects) to Amazon Bedrock Nova / Claude in the `toolResult` message block.

* **Steps Taken:**
  1. Handled incoming `toolUse` block with `toolUseId`.
  2. Captured tool execution result as a native JavaScript object.
  3. Passed `{ role: 'user', content: [{ toolResult: { toolUseId, content: [{ json: result }] } }] }`.

* **Expected vs. Reality:**
  * **Expected:** The model cleanly ingests the JSON object and proceeds with the next reasoning step.
  * **Actual:** In scenarios where the tool returned nested boolean flags (e.g. `fallDetected: true`, `bodyOrientation: "fallen_abnormal"`), the Bedrock endpoint occasionally threw `SerializationException: Expected string for content.text or valid JSON format in toolResult.content[0].json`.

* **Severity:** **Medium**

* **Workaround Implemented:**  
  Enforced explicit JSON serialization and schema normalization before returning results to Bedrock, ensuring every boolean or nested date was cast to strict JSON primitives.

* **Actionable Suggestion for Amazon:**  
  Provide clearer TypeScript type definitions in `@aws-sdk/client-bedrock-runtime` for `ToolResultBlock` that strictly enforce the allowed JSON shapes at compile time rather than relying on runtime AWS 400 errors.

### Friction Entry 3: Absence of an Official Local Alexa+ MCP Emulator for Push/Proactive Triggers

* **Task Attempted:**  
  Simulating an inbound proactive event (e.g., an accelerometer interrupt triggering Alexa+ without the user first saying the wake word "Alexa").

* **Steps Taken:**
  1. Reviewed existing Alexa Skills Kit (ASK) proactive event APIs vs. new Alexa+ Agent guidelines.
  2. Attempted to connect an MCP Server over SSE (`/mcp/sse`) to simulate how Alexa+ would maintain an ambient listening session.

* **Expected vs. Reality:**
  * **Expected:** An official, lightweight CLI simulator (e.g., `agy alexa simulate --mcp-server http://localhost:3001/mcp/sse`) capable of injecting proactive push events into the agent loop.
  * **Actual:** Gated developer preview tools are restricted, forcing developers to build their own end-to-end web simulator to prove agentic behavior.

* **Severity:** **Medium**

* **Workaround Implemented:**  
  Engineered a custom, high-fidelity **Echo Show 15 Web Simulator** (`src/components/EchoShowDisplay.tsx`) featuring real-time Web Speech synthesis, live ambient waveform rendering, and one-click scenario injection.

* **Actionable Suggestion for Amazon:**  
  Publish a community npm package `@amazon/alexa-plus-mcp-simulator` that lets any developer run a local browser-based Echo Show screen and feed it an MCP server URL. This would dramatically accelerate third-party developer adoption for Alexa+.

### Friction Entry 4: Ring Webhook & Smart Lock Authorization Staging for Emergency Scenarios

* **Task Attempted:**  
  Simulating dynamic temporary pin creation (`temporaryAccessCode`) and remote deadbolt disengagement during medical emergencies.

* **Steps Taken:**
  1. Evaluated Ring Developer SDK / Smart Home Skill API access for deadbolt unlocks.
  2. Attempted to trigger two-way audio broadcast over Ring Doorbell speaker via API.

* **Expected vs. Reality:**
  * **Expected:** A programmatic sandbox or simulator endpoint to test Ring Doorbell chime events and smart lock toggle states without owning a physical $250 Ring device.
  * **Actual:** No official mock API or virtual Ring device simulator exists for independent developers.

* **Severity:** **Low / Moderate**

* **Workaround Implemented:**  
  Built a virtualized `RingSecurityState` manager with automated access code generation (`911-EMT` / 4-digit temporary PIN) and simulated live video feeds (`src/components/RingCameraModal.tsx`).

* **Actionable Suggestion for Amazon:**  
  Introduce a "Ring Device Sandbox" inside the Amazon Developer Console allowing developers to send mock doorbell rings, motion detection events, and verify deadbolt unlock payloads in real time.

### Friction Entry 5: Cold Start Latency in Serverless Ambient Agent Pipelines

* **Task Attempted:**  
  Executing multi-step MCP agent loops (reading vitals -> checking medication -> unlocking door -> writing audit log) within the real-time threshold required for elderly voice interactions (< 2.0 seconds).

* **Steps Taken:**
  1. Chained 4 sequential MCP tool calls inside a single Bedrock agent invocation loop.
  2. Measured total round-trip latency from scenario trigger to spoken voice output.

* **Expected vs. Reality:**
  * **Expected:** Sub-1.5s latency for voice triage.
  * **Actual:** Sequential round-trips to Bedrock for each tool call accumulated to 3.8s–4.6s when using remote cloud endpoints without parallel tool execution.

* **Severity:** **Medium**

* **Workaround Implemented:**  
  Implemented batched MCP tool execution where non-dependent tools (e.g., unlocking the Ring deadbolt and recording the DynamoDB audit log) execute concurrently using `Promise.all()`.

* **Actionable Suggestion for Amazon:**  
  Support native parallel tool execution in the Bedrock Converse API for Alexa+ agent skills, allowing the foundation model to return multiple `toolUse` blocks simultaneously and execute them in parallel.
